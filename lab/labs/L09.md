## 4. Drill-E1 - Image a directory and prove integrity

**30 minutes. Runs in the container. Data: victim /home.**

**Objective.** Acquire a host's data and prove the acquisition is faithful.

**Run this.**

```bash
ssh -i /root/.ssh/id_lab -p 2222 analyst@127.0.0.1 'find /home -type f -exec sha256sum {} \; 2>/dev/null | sort'
ssh -i /root/.ssh/id_lab -p 2222 analyst@127.0.0.1 'tar -cf - /etc /home 2>/dev/null | sha256sum'
tar -cf - /etc /home 2>/dev/null | sha256sum
```

**What good looks like.**

```text
c9d5389609c95a350bf46b7f5562fbb2540bf487c1ed408c86c24874953f2935  /home/admin/.ssh/authorized_keys

80c03e282465331865f1ab5261020a8c39a0ffea8bc666a646e27a4115d69241  -

1d3d52b69334d5af5dba46a62bfacf3580505a842ca9965ebf061bf555de3428  -
56550400 bytes exported

Hash the readable set first, stream the file system through SHA-256 second, and export the container
third. The archive hash reproduces from the same state; the export hash changes whenever the container
changes, which is exactly why it is taken. The victim is a container with no block device and no sudo,
so the learner must say that a dd of /dev/sda is impossible here rather than pretend to run it.
```

**Save this evidence:** `image file, sha256 before and after` in `/labs/reports/`.

**Pass criterion.** Three artefacts with hashes, and the container limitation stated.

**Common mistake.** Running dd on a host that has no block device and no sudo.

## 5. Drill-E3 - Parse MFT and bitmap records

**35 minutes. Runs on kali. Data: ntfs1.raw, converted from the E01.**

**Objective.** Convert the acquisition, then read the MFT and recover a file by inode.

**Run this.**

```bash
ewfexport -u -q -f raw -t /labs/work/disk/ntfs1 /labs/work/disk/ntfs1-gen2.E01
fls -r /labs/work/disk/ntfs1.raw | grep -iE '(txt|pdf|jpg)$'
icat /labs/work/disk/ntfs1.raw 48-128-6 > /labs/reports/U09-E3-logfile1.txt
```

**What good looks like.**

```text
ewfexport: SUCCESS
MD5 hash calculated over data: 27a9053e35aac74608493e755353cb95

+ r/r 40-128-1:  20076517123273.pdf
+ r/r 48-128-6:  logfile1.txt
+ r/r 34-128-1:  NISTSP800-88_rev1.pdf
+ r/r 31-128-1:  NIST_logo.jpg
+ r/r 37-128-1:  report02-3.pdf
r/r 46-128-1:   EFS-key-info.txt

and the extracted logfile1.txt on disk. Note which inodes are allocated and which are not.

Why the conversion: the Sleuth Kit 4.14 in both images segfaults on this EnCase 6 file, which is
itself a lesson. The raw image is the working copy; the E01 stays unaltered as the exhibit.
```

**Save this evidence:** `MFT extract, deleted file list` in `/labs/reports/`.

**Pass criterion.** The conversion hash matches, and one file is extracted and readable.

**Common mistake.** Extracting by filename instead of by inode, which fails on deleted entries.

## 6. Drill-E13 - Live response on the victim

**25 minutes. Runs in the container. Data: the victim service on 127.0.0.1.**

**Objective.** Watch a live host for behaviour without stopping it.

**Run this.**

```bash
ssh -i /root/.ssh/id_lab -p 2222 analyst@127.0.0.1 'lsof -nP -i | head -8'
ssh -i /root/.ssh/id_lab -p 2222 analyst@127.0.0.1 'ps -o pid,vsz,args'
ssh -i /root/.ssh/id_lab -p 2222 analyst@127.0.0.1 'find / -mmin -60 -type f 2>/dev/null | head -5'
```

**What good looks like.**

```text
22   9.8m tcpdump -i eth0 -U -w /var/log/network.pcap
23    20m python3 /webapp.py

/home/admin/.ssh/authorized_keys
/sys/kernel/warn_count

tcpdump is writing a capture and the web app is listening, so the host is under live observation
already. The newest file is the key installed to get in, which is the analyst's own footprint showing
up in the analyst's own evidence. Saying so is part of the job.
```

**Save this evidence:** `socket and handle list` in `/labs/reports/`.

**Pass criterion.** Names the live collector and acknowledges the analyst footprint.

**Common mistake.** Presenting your own access as attacker activity.

## 7. Drill-E14 - Linux logs, shell history and ext4 basics

**30 minutes. Runs in the container. Data: ubuntu-ext4.img, fixture to author.**

**Objective.** Analyse a Linux image for logon, command and persistence artefacts.

**Run this.**

```bash
mmls /labs/work/disk/ubuntu-case.img
fls -r -o 2048 /labs/work/disk/ubuntu-case.img | grep -E 'auth.log|bash_history|updater|cron'
icat -o 2048 /labs/work/disk/ubuntu-case.img 31 | head -5
```

**What good looks like.**

```text
002:  000:000   0000002048   0000614399   Linux (0x83)

++ r/r 22:  .bash_history
++ r/r 14:  .cache-update
+++ r/r 19: updater.service
++ r/r 31:  auth.log

/var/log/auth.log
Jan 22 08:52:11 ubuntu-web01 sshd[2141]: Failed password for invalid user admin from 45.125.66.32 ...
Jan 22 08:53:02 ubuntu-web01 sshd[2190]: Accepted password for analyst from 10.1.17.90 ...

Brute force from the same host that runs the C2, then a successful logon from inside. Two
persistence paths: the cron file and the systemd unit.

Measured on the range: mmls 7 ms, fls 16 ms, icat 10 ms.
```

**Save this evidence:** `auth log timeline` in `/labs/reports/`.

**Pass criterion.** The offset is stated, and every artefact path is absolute inside the image.

**Common mistake.** Running fls on the raw image without the offset and concluding there is no filesystem.

## Handover brief

Two minutes at the end. Each learner answers three questions out loud, in 90 seconds:

1. **Finding.** One sentence a client would understand. No tool names.
2. **Limitation.** What this evidence cannot tell you, and why.
3. **Next step.** The single next action you would take, and who authorises it.

Record the three answers in `/labs/reports/` as the lab's closing note. This is group A4, record keeping, in practice.
