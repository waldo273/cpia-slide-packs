## 4. Drill-F9 - Process injection and SSDT hooks

**30 minutes. Runs on kali. Data: jo-2009.mem.**

**Objective.** Distinguish process injection evidence from a false positive.

**Run this.**

```bash
vol -q -f /labs/work/jo-2009.mem windows.malfind | head -8
vol -q -f /labs/work/jo-2009.mem windows.ssdt | head -4
strings -n 6 /labs/artifacts/malware/samples/cobalt_like.dll | head -10
```

**What good looks like.**

```text
928  csrss.exe  0x7f6f0000  0x7f7effff  Vad  PAGE_EXECUTE_READWRITE  ...  N/A
c8 00 00 00 cc 01 00 00 ff ee ff ee ...

Volatility 3 Framework 2.28.0
Index  Address  Module  Symbol
(no rows)

`.data
https://cdn.static-resources.test/microsoft-ph-update
\\.\pipe\MSSE-2679-server
jitter 25%
Mozilla/5.0 (Windows NT 10.0; Win64; x64)
XFwuXHBpcGVcTVNTRS0yNjc5LXNlcnZlcg==

malfind flags csrss as read, write and execute, which is ordinary for that process, and the SSDT is
clean, so memory alone does not support injection. The DLL argues otherwise: a command address, a
named pipe, a 25 percent jitter and a base64 copy of the pipe name. Injection is argued from the
artefact, not from one flagged region.
```

**Save this evidence:** `hook list` in `/labs/reports/`.

**Pass criterion.** False positive identified and the DLL evidence used instead.

**Common mistake.** Reporting csrss as injected because malfind listed it.

## 5. Drill-F12 - Behaviour from API calls and a sandbox report

**30 minutes. Runs on kali. Data: authored report excerpt.**

**Objective.** Describe behaviour from API calls and a sandbox report, mapped to ATT&CK.

**Run this.**

```bash
head -20 /labs/work/samples/sandbox-report-excerpt.txt
strings -n 8 /labs/artifacts/malware/samples/emotet_like.elf | grep -iE 'run|update|beacon'
```

**What good looks like.**

```text
Rows: Run key write (T1547.001), remote thread creation (T1055), beacon to
45.125.66.32:2917 (T1071.001), upload of 5.4 MB (T1041). Confidence falls for the injection row
because the report itself flags AVG's injector as a known false positive on the same image.
```

**Save this evidence:** `behaviour table, ATT&CK map` in `/labs/reports/`.

**Pass criterion.** Each behaviour has evidence and a technique id, with confidence stated.

**Common mistake.** Writing a narrative of what malware generally does rather than this sample.

## Handover brief

Two minutes at the end. Each learner answers three questions out loud, in 90 seconds:

1. **Finding.** One sentence a client would understand. No tool names.
2. **Limitation.** What this evidence cannot tell you, and why.
3. **Next step.** The single next action you would take, and who authorises it.

Record the three answers in `/labs/reports/` as the lab's closing note. This is group A4, record keeping, in practice.

## If you are ahead, or behind

- Ahead: take the last drill and redo it with the tool's limitation tested, for example run the same query a second way and reconcile the answers.
- Behind: drop the last drill and keep the evidence review. Never drop the handover brief, it is where the learning lands.
